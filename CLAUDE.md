# ai-hub-of-hubs-structure (Python package and distribution `hubofhubs`)

A public repository: the ESOI records and shared structure for assembling the best AI-intelligence hubs, one seat per
part of a mind, chosen by metric and refreshed weekly. Quest AI Runner is its production consumer. This file holds only
what differs from general practice; the `README.md` explains the idea.

## Rules

- **Public hygiene.** No real person names, email addresses, ids, organization-private details or absolute machine paths.
  The organization name SpiritualData and this repo's name are fine.
- **No em dashes** in any text, record or prompt.
- **Records are the source, kept beside the code.** `esoi/intent.csv` is the top intent; each solution's problems, ideals, solutions, implementations and metrics live once, in the sub-intent folder of the container that holds the solution (`hubofhubs/the_self`, `the_body`, `the_intelligence`, `the_world`, `the_consciousness`; rows that span containers in `hubofhubs/*.csv`), with a generated `README.md` in each; `esoi.toml` lists them under `[records] beside_code`, and `esoi records place --apply` puts a new row where it belongs (standard: `docs/reference/records-beside-code.md` in the esoi repository). Read them as one tree (`esoi.read_tree`), never one file. An AI writes
  the descriptive wording of specs from the code and the neighbouring records, with no confirmation marker
  (only the esoi skill's own core field names and questions need the owner). A solution with no built implementation reports a pending step ("no arm yet"); a specified alternative that is not built yet may be recorded, marked as not built.
- **Five containers, sub-intents beside the code.** The top intent holds five solutions, the containers The Self, Body, Intelligence, World and Consciousness (`the-self`, `the-body`, `the-intelligence`, `the-world`, `the-consciousness`); a new top-level solution needs Joshua's explicit approval. **Extend before adding a solution:** a new behaviour is first a case, a metric stage, an arm or a flow step of an existing solution; a new solution needs a distinct purpose no sibling holds, several alternatives competing on one metric, and a reason to exist if the task that raised it were forgotten ([explanation](../evolvable-structure/docs/explanation/extend-before-adding-a-solution.md)). The top of `hubofhubs/` shows only those five container folders plus `registry/` (the registry data); there is no other top-level code folder (layout and the old-to-new map: `docs/explanation/layout-of-the-hub.md`). Each container folder holds one folder per second-level solution, and that folder holds the solution's records, its `interface.py` and the code of its arms, beside the rows that name them in `filepath`; a solution with parts of its own has a folder per part, and one whose parts need their own paragraph and diagram is a sub-intent with an `intent.csv` (Intelligence: `mind`, `higher_mind`, `subconscious`, `critical_thinking`; World: `tools`, `model_plumbing`). Helper code with no arm of its own sits in the lowest folder its users share, with a generated arm-folder page and no records. Never add a code folder at the top of `hubofhubs/`. Display names lead everywhere (title case); ids stay as handles. `evidence_summary.MIND_TREE` is the approved tree the generated tables follow. Which container a part sits in follows what moves its metric: World with outside systems, Body with the system's data model or code, Intelligence with ML task accuracy, Consciousness with alignment to humans or policies.
- **Every solution states its role** (`purpose`, `out_of_scope`, `delegates_to`; `change_driver` on a container), and a new solution's role record carries the justification against each sibling, and the arms of one solution do the same job at the same level of specificity ([how-to](../evolvable-structure/docs/how-to/scope-the-role-of-a-solution.md)). The words Acting and `act-in-the-world` are retired. Connection scoring is a metric of Tools and Hands, not a solution.
- **The flow comes first.** Each composition arm (`flow.py` of each container and sub-intent, and `the_self/respond.py`) takes the solutions it uses as typed needs and calls each solution's declared entry point through `hubofhubs.the_self.steps.take`, in the order the intent's solution coherence paragraph says; the interface of every solution is declared in the `interface.py` beside the solution before any arm exists. A step whose solution has no arm yet is a `pending` step (`no arm yet`), never made-up output; the paragraph in `intent.csv` must match the code (`python3 -m esoi.structure.structure_check.coherence --gate`). The Self has no bypass call (no `answer`, `model_only`, `context_for` or `take_in`) and makes up no answer: a part with no arm is a pending step and the answer is what the Response Writer wrote. Integrity audits what the system says about itself and what it did; Response Quality judges answers to people against a `QualityProfile` (`hubofhubs/the_consciousness/representatives/quality.py`) resolved from the Representative, Guidance and Prioritization, with a default profile as the fallback.
- **An autopilot is built on Proactivity and Prioritization.** Proactivity (Intelligence) says what is due; Prioritization (Consciousness) says what matters first among it and the other waiting work; `IntelligenceComposition.proactive` and `SelfComposition.act_unasked` call both in that order. A consumer's events come through Body's Intake Sources (`attach_events`), never hub code, and its schedules and waiting work are mapped from its own data (`docs/how-to/build-an-autopilot-on-the-hub.md`, which `tests/test_autopilot_how_to.py` runs). Prioritization reads only fields the data carries and what the person stated; its cases are neutral and exercise one generic rule each (`evaluation/prioritization/build_cases.py`); a consumer's own ordering rules (its data model, its autopilot's instructions) are the consumer's own arm, scored under the same metric with cases built on it.
- **Adopt before writing, and prove the entry point.** Before an arm is written, each strong existing implementation (open source, the consumer's own, a sibling repo) is built on as an arm or recorded in `hub_findings.csv` with `adoption` (`arm`, `part` or `not_adopted`) and its reason; `tests/test_adoption_and_entry_guards.py` fails a guarded area with a finding that has neither. Every solution a person touches directly (the terminal, the front door) has a metric stage run through its real entry point (`evaluation/terminal_session/pty_stage.py` drives `ahohs work` on a pseudo-terminal with a real fast-tier session), because a perfect score on self-written cases only shows the arm does what it says.
- **Research is recorded as an investigation, before the change it informs.** Looking something up to decide a solution, an arm, a metric or a registry finding is one investigation (question, decision, criteria, queries, counted screening, graded items with URLs, known and unknown, limitations, a decision for each candidate, a revisit date), written in the same pass with `ahohs investigation record FILE.json` (or `hubofhubs.api.record_investigation`; the how-to is `CONTRIBUTING.md` section 5), never by hand-editing `investigations.csv`. A registry finding names it in `investigation_id`. Rule L1 (`scripts/esoi_rules.py`, set in `esoi.toml` `[rules.L1]`) checks this from its `since` date: advisory, then failing from `fail_from`.
- **Selection by metric only.** Set `selected` from the seat's metric result, never from preference.
- **Generic, no consumer content.** The hub holds real executing code (seats as Protocols, arms in extras). Core imports stay lazy and inside the arm (stdlib, the package and `esoi` outside an arm), and `pip install hubofhubs` carries the libraries the selected arm of every solution imports: the base `dependencies` are derived from the arms' `REQUIRES` and the selection by `python3 scripts/sync_dependencies.py`, never typed by hand (`hubofhubs/the_self/integrity/tests/test_base_dependencies.py`); the extras are for the alternatives that are not selected. No consumer-specific prompts or settings here; those stay in the consumer (QAR for Quest).
- **Generated blocks.** The README is written by hand; `docs/reference/status.md` (containers table, evidence table, not-measured list), `docs/reference/registry.md`, `docs/reference/evidence-by-arm.md`, `docs/reference/requirements-by-arm.md`, the headline lines of the two drafts in `drafts/`, `.env.example`, the marked `dependencies` lines of `pyproject.toml` (`python3 scripts/sync_dependencies.py`) and `hubofhubs/arm_order.json` (`python3 scripts/sync_arm_order.py`) are generated: run `python3 scripts/status.py` (also after any new result or arm declaration), then `PYTHONPATH=../evolvable-structure/implementations/python python3 -m esoi requirements --package hubofhubs --env-template .env.example`. Never edit between the markers or type a number into them. The plain words for each check are rows of `docs/reference/evidence-labels.csv`. The README stays under 200 lines; the area detail lives in `docs/reference/registry.md`.
- **Requirements are declared beside every arm** (`REQUIRES` on the class; shared pieces in `hubofhubs/the_self/assembler/arm_needs.py`; `()` for an arm that needs nothing). A key is `api(...)` with a secret `env(...)` and the official signup, docs and pricing links; a free-tier or rate-limit statement is copied from the vendor's own page, dated, and left out if it cannot be confirmed there. Python requirements name the extra of `pyproject.toml` that provides the module (`hubofhubs/the_self/integrity/tests/test_requirements.py` checks this). `ENVIRON` still works but new arms use `REQUIRES`. A new arm's `REQUIRES` is part of adding it; `docs/reference/requirements-by-arm.md` is its generated view. When a selected arm cannot run on this machine (library, key in the given mapping, program, option), the best-measured arm that can stands in (`hubofhubs/the_self/assembler/availability.py`, in the order of `hubofhubs/arm_order.json`, written by `python3 scripts/sync_arm_order.py` from the leaderboard); an arm the caller names is kept.
- **The front door works on a plain install** (only a logged-in Claude CLI, no vendor key; `docs/explanation/the-front-door-on-a-plain-install.md`). A flow step is declared by its call: `take` for a step the answer depends on, `hubofhubs.the_self.steps.support` for one that only enriches (context, retrieval, a check, a record, web search); a supporting step that cannot run never fails the answer. The person sees nothing when a stand-in arm did the job (it is `Result.stood_in`, a detail), one short plain line in `Result.note` only when the answer is materially weaker and they can act on it, and the real stop reason in `Result.stopped` (never "budget" for a missing library). The test of any message: if it would appear for most people on a plain install, fix the default or do not say it. A question about the hub is answered from its own records, a named file is read, not searched for. Pinned by `tests/test_out_of_the_box.py` and the metric `plain_install` (`esoi run plain_install --impl front_door --max-calls 60`: zero warnings per case).
- **Docs are in four folders** (`docs/tutorials`, `docs/how-to`, `docs/explanation`, `docs/reference`) with the index `docs/README.md`; `esoi docs check` must pass. Announcement and article drafts live in `drafts/`, outside the docs. The wiki is generated (`esoi docs wiki --out DIR`), never edited.
- **The registry** is `hubofhubs/registry/*.csv`. A capability is a hub connection (a class, counted once), never one service;
  a single service a consumer hand-wires goes in `hub_integrations.csv`. Facts need a dated source; see `docs/how-to/refresh-the-registry.md`.
- **Tests sit beside the code they test**, in a `tests/` folder of the lowest solution folder their imports share (`hubofhubs/the_intelligence/subconscious/tests/`, and so on); `tests/` at the top holds only cross-cutting tests and the shared support (`support.py`, `act_support.py`, `fixtures/`), and the root `conftest.py` serves them all. Run a test by its file path. Tests are not shipped (`pyproject.toml` excludes them) and the package-wide scans (import boundary, consumer words) skip them. Evaluation components stay in `evaluation/`.
- **One front door.** A consumer reaches a part only through `hubofhubs.run("<id>", ...)`, the typed handle `hubofhubs.run(Interface)` and the names of `hubofhubs/api.py` (`LOCATIONS`, resolved lazily, `__all__`); a hub move edits that one table, never a consumer. A moved or new module that a consumer needs gets an entry there; every interface must be exported (`tests/test_public_api.py`), and README, tutorials and how-tos import only from `hubofhubs.api`.
- **Consumers** hand this package a `Binding`; the package never imports a consumer. Core imports stay stdlib, the package and `esoi` (`tests/test_import_boundary.py`); a third-party library is imported inside the arm that needs it, declared by that arm's `REQUIRES`, and listed in the base install when the arm is selected and in a per-arm extra otherwise.
- **No environment reads, one exception.** Only the user-facing entry functions (`assemble`, `run`, `stream`, `needs`) read `os.environ`, through `hubofhubs.the_self.assembler.resolution.process_environment()`, and only when the caller gave no `environ`; every core module takes the mapping (`tests/test_no_environment.py` pins this). Settings are `AssemblyConfig` fields (`selection_environ` is the only environment `esoi` sees). Names are validated, never import paths. A seat is a `typing.Protocol` declared with `@solution(id)` in the `interface.py` of its folder (`resolution.interface_modules()` finds them); an arm's constructor parameters typed with a seat are its needs. No alias for a renamed package or arm. Read `docs/explanation/resolution-design.md` before changing resolution or assembly.
- **Generic assembly, selection, cascade and checking belong in esoi, not here;** see `evolvable-structure/docs/explanation/what-belongs-where.md` (when unsure, propose the change to Joshua).

## Measuring

A changed file only informs; it does not order a metric run. `esoi run --stale --plan` lists which recorded results no longer describe the
code (the changed file and the component that owns it) and why each is or is not re-run, and `esoi check --strict` gives the same as advice
that never fails. Run a metric when what it teaches is worth its cost: improve the arm first, rerun only failing cases, run the whole set
when they pass, and re-record the selected arms when a decision or release depends on them (`esoi run --stale --for-decision`, or name an arm
with `--include seat/arm`; `--all` is the old run-everything). No commit hook and no CI step runs metrics. A row is stale only when code the
arm measures changed (esoi's `import_closure` rule: the files the arm's module imports, found by reading the source); `esoi stale --explain
<seat>` shows which. An offline run refuses to start a model command (esoi's harness sets `ESOI_OFFLINE=1` and blocks `claude`, `codex` and
`gemini` unless the arm declares `PAID = True` or is run with `--max-calls`), so the `claude_cli` fallback to `~/.local/bin/claude` cannot spend
money in an offline run.

Generic mechanics belong in esoi (`evolvable-structure`) and are edited only on the owner's own prompt, never from here.
